Quickstart guide

How to run API Surface Mapper, how to read what it gives you, and what it deliberately does not claim.

← Back to the mapper  ·  Setup guide

What this tool is for

It answers one question: what public API surface does this domain expose that a browser can see from the outside? No login, no agent, no scanner to install. You type a domain and it assembles evidence from three independent sources in about twenty seconds.

Typical uses: a first pass on your own organization before someone else does it, a sanity check that a documented API catalog matches reality, or a quick look at a vendor or acquisition target during due diligence.

Sixty-second quickstart

  1. Enter a bare domain. Use the registrable form, like stripe.com. Scheme, www., ports and paths are stripped for you, so pasting a full URL is fine.
  2. Press Map surface or hit Enter. The status strip shows which phase is running.
  3. Read the three counters. Documented, live hosts, and to verify. They correspond to the three colors in the results below.
  4. Work the amber and blue rows. Green is already confirmed. Amber and blue are where your attention pays off.
  5. Click Copy verification commands and run them in a terminal. That converts blue candidates into facts.
  6. Click Copy results as JSON if you want to keep the run or diff it against a later one.

How to read the results

Every row carries an evidence tier. The tier tells you how much the tool actually knows, which is the whole point of the design.

Documented documented

Either the domain appears in the APIs.guru open directory with a machine-readable spec, or the browser successfully read a spec file directly from the host.

What it means: the API is real, public, and described. Open the spec URL and you have the endpoint list, parameters and schemas without guessing.

Live host live host

An API-style hostname such as api.example.com resolved in DNS at the moment you ran the scan.

What it means: the name exists. It does not mean an API is listening, that it is open, or that it is in scope for testing. Resolution is existence, not exposure.

Verify manually verify

A well-known spec path on a host that really resolves, which the browser could not read. Almost always this is a cross-origin block rather than a missing file, and the browser cannot tell the two apart.

What it means: unknown, and worth thirty seconds of your time. This is the queue the verification commands exist to drain.

What the scan actually does

Three phases, in order.

1. Directory lookup

Fetches the APIs.guru list and matches your domain against known providers. Anything that matches comes with a real OpenAPI or Swagger URL. This phase produces the green rows.

2. Hostname resolution

Builds roughly forty five API-style hostnames from a fixed wordlist and resolves each one over DNS-over-HTTPS, using Google and Cloudflare as resolvers. The wordlist covers the usual shapes: api, gateway, graphql, developer, version prefixes like v1, environment names like sandbox and staging-api, identity hosts like auth and sso, and event hosts like webhooks. Whatever resolves becomes an amber row.

3. Spec path probing

Takes the apex plus the hosts that resolved, up to eight origins, and attempts a direct read of each well-known descriptor path on each one:

PathWhat a hit tells you
/openapi.json, /openapi.yamlFull OpenAPI 3 description of the API
/swagger.json, /swagger/v1/swagger.jsonSwagger 2 description, often an older service
/v3/api-docs, /v2/api-docs, /api-docsSpringdoc or Springfox defaults, common in Java stacks
/.well-known/openapi.jsonSpec published at the standard discovery location
/.well-known/openid-configurationAn OIDC provider, with its token and authorization endpoints
/.well-known/oauth-authorization-serverAn OAuth 2 authorization server and its metadata
/.well-known/security.txtA published contact route for reporting what you find
/graphqlA GraphQL endpoint, which is one URL hiding an entire schema

Reads that succeed become green rows with the title, version and declared servers pulled out of the spec. Reads that fail become blue candidates, but only when the origin host actually resolved, so the list stays free of invented hostnames.

Verifying the candidates

Click Copy verification commands and paste into a terminal. Each line prints a status code and content type without downloading the body:

# Run these to confirm each candidate endpoint.
curl -s -o /dev/null -w '%{http_code} %{content_type}  https://api.example.com/openapi.json\n' \
  'https://api.example.com/openapi.json'

How to read what comes back:

ResultRead it as
200 with a JSON or YAML content typeA real published spec. Promote it to documented and open it.
200 with text/htmlA catch-all page or SPA shell, not a spec. Discard.
401 or 403Something is there and it is protected. Interesting, and correctly configured.
404Nothing at that path. Discard the candidate.
405The path exists but rejects GET. Common for /graphql, which usually wants POST.
000 or a timeoutNo listener, or the connection was dropped. Nothing to chase.

The tool cannot do this step for you. That is not an oversight, it is the browser security model working as intended.

The OWASP mapping

Each finding carries a chip linking to the relevant category of the OWASP API Security Top 10 (2023), and the review panel underneath collects the categories your results actually touched. The mapping is deliberately simple:

  • Identity hosts such as auth, sso and oauth, plus OIDC and OAuth metadata documents, map to API2 Broken Authentication.
  • GraphQL endpoints map to API4 Unrestricted Resource Consumption, because one URL can accept an arbitrarily expensive query.
  • Webhook, integration and partner hosts map to API7 Server Side Request Forgery, since those are the places an API fetches URLs you supply.
  • A readable spec maps to API3 and API8, because the schema shows you exactly which properties are exposed and whether the deployment leaks more than it should.
  • Everything else maps to API9 Improper Inventory Management, which is the honest headline for the whole exercise. Discovery is an inventory problem first.

Nothing here is a vulnerability finding. A chip is a prompt to review, not proof of a flaw. The risks that actually cause breaches are authorization flaws: API1 Broken Object Level Authorization, API5 Broken Function Level Authorization and API6 Unrestricted Access to Sensitive Business Flows. All three are invisible to passive discovery, because seeing them requires sending authenticated requests and comparing what different users get back. No amount of external mapping substitutes for that.

Limits worth knowing

  • It is a wordlist, not enumeration. Hosts outside the roughly forty five names in the list are simply never tried. Real subdomain enumeration needs certificate transparency logs and passive DNS, which a browser cannot query freely.
  • Cross-origin rules cap what it can read. Any host that does not opt into cross-origin reads stays unreadable, permanently, no matter how public its API is.
  • Only A records. A host that exists solely as an AAAA or an unusual record type will be missed.
  • It is a snapshot. DNS answers reflect the moment you ran it. Re-run and diff the JSON if you care about change over time.
  • Directory coverage is uneven. APIs.guru is broad but not complete, so an absent entry means nothing.
  • Nothing is proxied, but the lookups are not invisible. There is no backend, so every request runs from your browser and your own IP and nothing you search is logged by this page. The DNS resolvers and the public directory it queries do see the domain, and the target host sees the spec path requests. If a lookup needs to be unattributable to you, this is the wrong tool.

The first three are browser limits, not tool limits. The optional server engine below lifts all three. The last three apply to both engines.

The server engine

A browser is a poor scanner: it cannot query certificate transparency logs, cannot read a response from a host that does not opt in, and cannot see a single response header. A small Python service removes all three restrictions. It ships in this repository under server/, and it serves this guide and the tool itself, so there is nothing to configure:

docker compose up --build

Open http://localhost:8000 and a Server engine badge appears under the domain input. The link beside it switches back to the browser engine whenever you want to compare the two. If the container is not running, the page behaves exactly as it always has.

StepBrowser engineServer engine
HostnamesA fixed list of about fifty guessesEvery name issued a certificate, from crt.sh or Cert Spotter, merged with the guess list and ranked so confirmed names probe first
DNSOne A record lookupFull CNAME chains, AAAA, wildcard detection, and dangling CNAMEs flagged as takeover candidates
Reading responsesBlocked by CORS on hosts you do not controlRead directly, redirects followed one hop at a time
SpecificationsTitle and version, when the read succeeds at allPath and operation counts, declared auth schemes, every operation that declares no authentication, and the widest object schema
OpenID ConnectListed as a candidate URLIssuer and endpoints parsed, with implicit and password grants and none client authentication flagged
GraphQLThe hostname, nothing moreAn introspection query is sent and the exposed type count reported
HeadersInvisibleCORS reflection and credentials, version banners, missing HSTS

The blue verify manually tier mostly disappears under the server engine, because the whole reason a finding landed there was that your browser could not read it. What remains blue is what is genuinely unknown: a request that timed out, a host that errored, or a name whose CNAME target has been deprovisioned.

Two things it does deliberately, so the output does not mislead you. A host that answers identically on every probed path is reported once as host-wide behaviour rather than as a dozen protected endpoints, because a CDN returning 403 to everything is one fact, not twelve. And on a domain with a wildcard DNS record, names that match only the wildcard are dropped, since otherwise every guess would appear to resolve.

The container binds to localhost only and runs unprivileged. Before it opens any connection it resolves the hostname and rejects private, loopback, link-local and cloud metadata addresses, and it re-checks on every redirect, so a hostile DNS record cannot turn your scanner into a proxy into your own network. Set SCOPE_ALLOWLIST in docker-compose.yml to restrict it to domains you are authorised to test. It stays passive throughout: it reads what is published and sends one GraphQL introspection query. It does not authenticate, fuzz, or attempt any exploit.

Exporting a run

Copy results as JSON gives you the whole run in a stable shape, suitable for saving alongside a report or diffing against a later scan:

{
  "domain": "example.com",
  "engine": "browser",
  "documented": [ { "provider": "...", "title": "...", "spec": "..." } ],
  "live": [ "api.example.com", "auth.example.com" ],
  "candidate": [ "https://api.example.com/openapi.json" ],
  "owaspReviewAreas": [ "API9", "API2" ]
}

Troubleshooting

Everything came back empty

Check the domain form first. It wants a registrable domain, so example.com rather than docs.example.com. If the domain is right, an empty result is a real result: plenty of organizations expose no API-style hostnames under common names.

"Could not reach the public directory"

The APIs.guru fetch failed, usually a network block or an extension interfering. The other two phases still run, you just lose the green directory rows.

Nothing was directly readable

Expected, and stated on the page when it happens. Most APIs correctly refuse cross-origin reads. Work the candidate list with the copied commands instead.

A host resolves but nothing responds

Common and benign. Wildcard DNS makes every name under a domain resolve, and plenty of names point at infrastructure that answers nothing on 443. Verification is what separates these from real endpoints.

Scope note. Resolving a hostname and requesting a published document is ordinary, unauthenticated traffic. Testing what you find is a different activity. Confirm you have authorization, or an in-scope bug bounty program, before you go past reading public documents.
